# 最大尺寸 RSS 复核与后续修复方案 — UP-03 v1.0

日期：2026-09-13。状态：**DEFERRED / planned_not_implemented；用户已接受该偏差为本机已知问题，延期排查**。不自动重置 UP-02 的 R/F 计数，不改变性能预算。

## 当前需要解决的具体问题

缩放 CPU 的 6 行承载层修复已在构建 9mXYWr 上通过两次独立 30+300 秒测量（13.79705% / 13.8288%）。但最大尺寸的完整验收未通过：RSS 斜率 2.72570466 MiB/min，首末分钟差 9.171875 MiB，超过 ≤1 / ≤5 的既定预算。完整产品尚未闭合。

[原始最大尺寸场景](evidence/WP-06-performance-20260913T122902Z/large) 中，第 164→165 秒 RSS 从 82.5625 跳到 91.65625 MiB；同一秒首次发生完整帧逐像素相等判断，此后 RSS 基本持平。应用纹理分配与保留最新缓冲均始终为 1。证据支持“首次完整 CPU 读取引发缓冲页面驻留”这一假设，但尚无 VM 分类和缓冲真实行跨度数据，不能将相关性写成已证明的唯一根因，也不能直接称为泄漏。

UP-02 的元数据候选只跳过明确零变化帧，仍观察到完整相同比较；没有证明消除了上述触发条件。单次增长提前进入预热造成的通过不等于修复。其数据保留，候选不晋级。当前交付构建与状态以 [UP-02 工作包](workpacks/UP-02.md) 为准。

## 不变的验收条件

- 主体 800×100 物理像素，完整光效、精确静态去重与采样新鲜度不变。
- 不删除、合并或延迟现有诊断记录；不把近似哈希相等当作像素相等。
- 不预先触碰全部缓冲来把后续内存增长挪入预热，不修改正式 fixture 轨迹、30+300 秒测量窗口或原阈值。
- 不因来源解释了可能机制就把失败结果改为 PASS；不以单次重跑通过否定原失败。
- 本机范围保持 M4 / macOS 26.5.2 / 内置 2x；其他环境未验证。

## 执行顺序与交付

1. **限定归因。** 保留 9mXYWr 失败基线；只在独立诊断构建中记录首次完整相同比较前后的进程 RSS、可用的物理 footprint/VM 分类、两块缓冲的真实尺寸/行跨度和比较耗时。记录数量限制为首次 4 个事件，关闭诊断后不保留常驻探针。VM 工具只针对本项目 PID；工具不可用时明确记录证据缺口，不扩大权限或扫描其他应用。
2. **验证触发条件。** 诊断场景分别覆盖持续变化、变化转静止、静止恢复变化、最大尺寸与默认尺寸。允许新增明确标注的诊断 fixture，但原正式验收 fixture 不变；诊断数据不替代预算。目标是确认页面驻留来自哪条读取路径、是否有真实缓冲池扩张，以及累计最大值是否有界。
3. **据证据选一个候选。** 只有确认可避免的持有、重复映射或分配时，才做对应的最小修复。缺少证据时不再叠加 layer 参数、不用人工预热掩盖波动。若必须引入 GPU 精确比较或改变内存验收语义，先提交具体资源/时序/指标差异供确认；不能把新增 GPU 工作藏出提交计数或把旧门槛直接放宽。
4. **正式收尾。** 候选必须通过受影响路径的检查、两次独立正式缩放及固定构建完整本机性能/恢复/视觉验收。所有首次读取和恢复路径均须覆盖；包内二进制与实测构建一致。没有完整通过时保留未闭合。

每步产出原始诊断、归因结论、候选差异与独立通过/失败结果。最多 3 次只读 R / 2 次对应 F；最终视觉最多 2 次并计入 R。轮次耗尽仍有问题则停止并报告，不自动另起工作包。

## 资料依据及适用边界

[Apple WWDC22](https://developer.apple.com/videos/play/wwdc2022/10155/) 将 dirty rects 定义为相对上一帧的变化区域，可用于减少重复处理；[WebRTC 源码](https://webrtc.googlesource.com/src/+/f7c1d7e4d3c1fe207eef6ed6251812cb6b982644/modules/desktop_capture/mac/screen_capturer_sck.mm) 使用零面积矩形识别未更新，并注意尺寸重配后的元数据。它们支持尝试元数据优化，不能证明每个像素相同的完整帧都会附带零变化标记，也不能证明本机 RSS 原因。

此前 CPU 的文献与论坛推理保留在 [UP-02 修复方案](缩放CPU修复方案-v1.0.md)。本方案不将论坛个案、单次 PASS 或工作计数替代本机因果证据。
