# WP-09 性能优化依据与论坛对照

检索日期：2026-09-13。用户要求补充文献和论坛观点。本资料用于解释优化假设与取舍；验收结论仍以 [工作包记录](workpacks/WP-09.md) 和 [最终报告](最终验收报告-WP09.md) 为准。

现有依据支持优先检查承载视图的重复布局/绘制，并保留实际 drawable 像素与窗口几何一致。它们不能证明本项目 CPU 超限只有一个根因，也不能代替本机五分钟测量。以下“文献”是 Apple 技术文档、技术讲座和作者实验记录，没有把论坛帖子称作同行评审论文。

## 与本机证据的对应

1. R3 的正式缩放 CPU 中位数为 **15.03665%**，略超 15%；R4 为 **16.44%**，仍不通过。R4 的帧率、间隔、GPU 时间、延迟和稳态内存均通过。这说明 F3 的两处调整不足以解决 CPU 门槛，不能用“理论上应该更快”覆盖实测。[R3](evidence/WP-07-resize-20260913T101343Z/result.json)、[R4](evidence/WP-07-resize-20260913T103146Z/result.json)
2. [有限调用栈](evidence/WP-07-resize-20260913T102041Z/cpu-sample.txt) 中出现窗口提交、隐藏 fallback 布局、AppKit 绘制和诊断写入路径。采样包含等待中的调用栈，出现次数不是精确 CPU 成本占比；不能把 `iokit_user_client_trap` 或文件等待次数直接当成忙 CPU 百分比。
3. F4 使用 layer backing / 按需重绘缓存透明承载内容，保留可见 carrier/fallback 的尺寸重绘，并避免重复设置相同鼠标穿透状态；撤回 F3 的延后 display。Metal 光效、drawable 像素口径、诊断记录数、测试尺寸及预算未降低。
4. F4 的 10～40 秒短测有 30 个 CPU 样本，中位数 **10.9405%**，呈现中位数 29 FPS、间隔 P95 41.666583 ms。它只支持继续验证该方向，不能与旧构建五分钟数字拼接成正式通过，也不能声称已测得精确节省比例。[短测 CPU](evidence/WP-07-resize-20260913T104049Z/cpu-diagnostic.json)、[呈现诊断](evidence/WP-07-resize-20260913T104049Z/result.json)

## 判定方式

以最终固定构建重新核验缩放 CPU ≤15%、呈现中位数 27～30 FPS、间隔 P95 ≤50 ms，以及既有延迟、内存、恢复和视觉门槛。透明缓存不能留下旧降级底板，不能改变光效或引入圆角毛边；静态不能新增重复 GPU 提交。若 R5 仍有 finding，按现有规约标记 BLOCKED_STALLED，不因文献或论坛意见放宽数值。

这些资料支持的是优化机制与可验证假设。当前任务不提供整机瓦数结论，也不以旧系统帖子代替当前本机验证。


## R5 实测反馈（2026-09-13）

最终 RrZwDN 构建的五分钟缩放 CPU 中位数为 **15.7364% >15%**，其他五类检查通过，见 [正式结果](evidence/WP-07-resize-20260913T104528Z/result.json)。因此 F4 的短测改善不能作为正式预算通过或稳定收益证据。文档解释了缓存为何可能减少工作，但尚未证明本管线的主要忙 CPU 来自该处；论坛的 drawable 等待个案也不是本机根因。后续应先区分忙 CPU、等待及布局/绘制、窗口提交、诊断写入的贡献，不能只据调用栈出现次数选修复。

本工作包已按 R5 上限标记 BLOCKED_STALLED，详见 [最终报告](最终验收报告-WP09.md)。未自动开启新工作包，未修改预算；旧构建通过项没有拼接成当前构建通过。

用户随后要求先制定修复方案。新增 [缩放 CPU 修复方案 v1.0](缩放CPU修复方案-v1.0.md)，状态 planned_not_implemented，未启动新工作包。

新增依据包括 [Apple WWDC25 CPU 分析](https://developer.apple.com/videos/play/wwdc2025/308/)、[WWDC23 线程阻塞分析](https://developer.apple.com/videos/play/wwdc2023/10248/)、[文件写入优化](https://developer.apple.com/documentation/xcode/reducing-disk-writes)、[signpost 区间记录](https://developer.apple.com/documentation/os/recording-performance-data)，以及 [Swift Forums 的 Apple DTS 文件 I/O 解释](https://forums.swift.org/t/task-safe-way-to-write-a-file-asynchronously/54639/7)。方案 §3 按来源列明适用范围；重点是区分忙 CPU 和等待、量化同步几何 JSON 路径，不把后台化等同于总 CPU 降低。

代码复核还发现 `check_geometry.py` 使用几何文件出现时间触发截图，因此异步写入存在取证时序约束。方案要求保持完整记录及真实几何关联，不能通过禁用诊断、延后积压或拉伸旧 drawable 获得验收通过。
