# WP-07 圆角毛边排查

日期：2026-09-11。结论：已复现实际 drawable 分辨率错误并修复；过渡截图已复核。WP-07 整体仍执行中，完整性能预算尚未重新验证。

## 根因与证据

用户指出的原图为 [window-6.50.png](evidence/WP-07-motion-20260911T072507Z/window-6.50.png)。这是原生窗口截图，主体放大后圆角和细边出现明显阶梯。

代码设置 `MTKView.drawableSize` 后，直接调用底层 `CAMetalLayer.nextDrawable()`。这条路径没有落实 MTKView 的延迟尺寸更新。诊断运行 [073819Z/process.log](evidence/WP-07-motion-20260911T073819Z/process.log) 显示：

- 屏幕 backingScale=2，底层 contentsScale=1。
- 初始请求 824×124 px，实际 drawable.texture 只有 412×62 px。
- 放大至请求 1624×524 px 时，实际纹理仍为 412×62 px。

低分辨率轮廓被拉伸到窗口尺寸；shader 抗锯齿宽度却按 2x 屏幕计算，边缘采样与实际像素密度不一致。仅关闭 MTKView 自动尺寸或同步呈现，均未消除这项错误。外发光/内发光的非均匀分布不是此次阶梯毛边的主因。

排查过程中增加的同步呈现检查又暴露了过渡坐标问题：[074048Z/process.log](evidence/WP-07-motion-20260911T074048Z/process.log) 中，计算主体 `{402.327491…, 50.558597…}` 经 AppKit 提交后成为 `{403, 51}`，原点也向下取整。精确坐标比较因此拒绝新帧，旧画面继续随窗口拉伸。此项与分辨率错误分别修正，不将初步“呈现不同步”假设当作唯一根因。

## 修复

1. 在取得 drawable 前，明确设置实际 CAMetalLayer 的 contentsScale 和 drawableSize；核对返回纹理的真实宽高，失败时报告错误。
2. 原生窗口几何在渲染前统一到 AppKit 使用的整点坐标与尺寸，并保持屏幕约束；默认主体仍为 800×100 显示像素。
3. GPU 完成后将对应窗口几何与 drawable 一起提交；保留过期目标检查、单个 GPU 在途上限和刷新节流。
4. 动态检查脚本现在逐帧验证实际纹理尺寸、图层比例及窗口坐标，并检查每张截图都有可见主体。诊断日志仅在显式测试开关下输出。

## 验证

最终构建 `9xnRJp`，签名有效，构建无警告。17/17 支持模块检查、6/6 恢复时序检查通过，见 [检查日志](evidence/WP-07-checks-F1-corner-final.log)。

[最终动态检查](evidence/WP-07-motion-20260911T074412Z/raster-check.json)：71 帧实际纹理尺寸匹配、0 个窗口坐标不匹配；22 张截图均有可见主体，结束后停止重复绘制。已查看移动、放大过渡、靠边与最终默认尺寸截图；圆角阶梯和旧轮廓拉伸已消除。截图时刻对应同一探针时间，因异步准备耗时不同，不保证不同运行在该时刻具有完全相同尺寸。

## 性能边界

没有新增高斯模糊 pass、超采样或常驻动画。恢复默认正确分辨率后，最终 drawable 像素数相对于错误的 412×62 为四倍；这不是 GPU 总耗时必然四倍，采样和模糊分辨率没有因此同比变化。

此前 WP-06 报告记录的是历史构建，未逐帧验证实际 drawable.texture 尺寸，不能作为本次修复后分辨率和呈现管线的性能验收。完整默认/动态几何预算及最大尺寸资源测量继续归入 WP-07 的 R07-03；在完成前不宣称当前构建已通过完整性能或功耗验收。
