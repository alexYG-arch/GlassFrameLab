## 1. 建议的首版范围

采用 `NSVisualEffectView` 的 behind-window 系统材质承载真实窗后模糊，叠加独立透明光效层。保留 800×100 物理像素空框、零偏移外扩散、圆角、右键开关/关闭、拖动及缩放行为。系统模式不得启动 `LocalCaptureService`、请求录屏权限或获取窗口外像素。

首版复用现有 `.hudWindow` 降级材质作为可运行起点，但它不是最终视觉已确认的目标；已有降级路径只证明系统材质承载可用，当前并不运行流光。底材先做白/灰/深背景的同位置对照，再决定是否继续迁移。避免先把系统材质改成不透明底板来追求一致。

Light 保留仅柔光、Dark 保留细线和柔光；两者仍使用品牌蓝/紫、原周长进度与首尾包络。**建议按系统/产品主题选择 Light/Dark，这是待验证的产品取舍，尚未改代码。** 系统底材可以自行响应背景，但公开 API 不向应用提供当前自定义统计所需的后方像素和亮度系数。若坚持对其他应用后方的实际像素进行相同判断，就不能同时保证取消当前屏幕采样权限。

如果后续效果只覆盖产品自己绘制的内容，可由产品直接提供主题或内容亮度；这与当前覆盖其他应用的桌面悬浮框不同。

## 2. 开发成本估算

以下为熟悉当前项目的 macOS 工程师有效工作量估计，以 1 人日约 8 小时计；不是执行时长承诺或已测工时。范围限定当前本机环境、一次主方向调校，不含多轮主观反复、签名公证上线和其他系统/显示器认证。

| 阶段 | 工作 | 估计 |
| --- | --- | --- |
| S1 原型 | 原生底材独立启动、无采集/权限请求；同位置对照基础材质 | 0.5–1 人日 |
| S2 光效与状态迁移 | 将流光从背景渲染中拆出，保留 Light/Dark 视觉规则、独立开关、拖动/缩放冻结和恢复 | 1–2 人日 |
| S3 调校与验证 | 首尾和圆角、主题切换、隐藏/显示、正常 app 无录屏权限启动、短资源对照 | 1–2 人日 |
| 合计 | 可评审的本机系统版本 | **2.5–5 人日** |

如果只看没有流光的系统毛玻璃底材，成本主要是 S1；不能将 S1 的完成当作整个替换完成。

估计依据：`FramePanel.swift` 已有 `PassiveVisualEffectView` / `.behindWindow` 原生材质、圆角及透传处理；窗口几何和 `BorderFlowClock` 可复用。主要改动在 `main.swift` 与 `RealtimeGlassController` 的采集/渲染绑定，以及 `GlassRenderer` 中目前与背景纹理同 pass 的光效合成。不是只替换一个控件就能保留全部行为。

## 3. 与当前效果的差异

| 项目 | 当前自定义版 | 系统分支预期及限制 |
| --- | --- | --- |
| 真实窗后模糊 | 应用采集局部背景后自定义 Metal/MPS 模糊 | 系统合成，仍可真实模糊窗后内容；应用不拿到背景像素 |
| 模糊/透明度 | sigma、饱和度、底色及明暗参数可精确调校 | 材质由系统控制，可选语义材质但没有等价的精确 sigma 参数；透明感和染色可能明显不同 |
| 明暗判断 | 读取框体后方像素统计，可独立于系统主题 | 系统底材自行处理；附加流光首版拟跟随系统/产品主题。浅主题覆盖黑色窗口时，附加光效不会自动复现原像素判定 |
| 流光与映射 | 直接与背景模糊结果在同一 shader 合成 | 路径、长度、蓝紫进度和时钟可复用；改为透明叠加，最终颜色和深度需要重调，不能承诺逐像素一致 |
| 内光/内阴影 | 自定义非均匀深度分布 | 可以保留额外自定义层，但需避免与系统自带的亮边/阴影叠加成双边或显脏 |
| 外形与操作 | 无标题栏的圆角空框、右键关闭、运动冻结 | 可保留，不需要恢复系统标题栏或红黄绿按钮 |
| 系统变化 | 主要由自有 shader 控制 | 更依赖系统版本、外观以及降低透明度等辅助设置；应接受系统的可访问性行为 |
| 用户权限 | 需要屏幕录制，当前新包尚未授权 | 系统模式本身不需录屏；保留视觉与窗口交互也不需要额外摄像头、麦克风、辅助功能权限 |

视觉预期是更接近系统材质，精确还原度下降；系统版不保证天然更通透。尤其当前 `.hudWindow` 底材可能比已调好的自定义玻璃更厚、更有中性底色，需要先看实际对照。

## 4. 运行与维护成本

预计可移除本模式的屏幕采集流、帧队列、像素变化检查、局部模糊纹理与亮度统计；采集权限及启动恢复状态也可以从系统后端退出。这些是减少应用内工作和维护复杂度的依据。

**不承诺 CPU/RSS 下降百分比或总功耗一定下降。** 模糊工作转由系统合成器/WindowServer 承担；只看应用 RSS/CPU 会漏掉这部分成本。流光开启时仍有动画提交，关闭时应让自有动画停止，但系统还会随后方画面更新材质。不得为了不采屏而用快照造成冻结背景。

验证沿用最小成本原则：只做同一背景、相同尺寸、相同流光开关下的短对照，关注应用与 WindowServer、GPU 和卡顿；与功能探针复用观察段，不重开长时间 RSS 专项。U02-06 是当前自定义版已知问题，系统版资源是否改善须独立观察，不能直接宣布解决。

## 5. 实施与验收顺序

1. 独立系统后端使用单独启动入口，绕开采集创建和权限请求；不把“权限不足后的降级”冒充系统主路径。
2. 在相同底图、尺寸、位置比较原生底材与已确认自定义版；若透明感偏差不能接受，保留分支并停止扩大迁移。
3. 拆出透明光效叠加，复用几何/颜色进度与时钟，明确主题来源；Light 仅柔光、Dark 细线加柔光。系统底材不允许上层出现不透明填充遮挡。
4. 正常 app 在未授予录屏权限时启动并验证，确认无采集实例、无权限请求、后方实时更新。保留拖动/缩放冻结与恢复、开关、隐藏/显示、once 和右键关闭检查。
5. 对照视觉、短资源及剩余问题后交由用户选择是否采用；分支存在不等于替换当前产品。打包仅在用户要求时执行。

### 另一条系统路线

本机 macOS 26 也可评估 `NSGlassEffectView`，它提供 Liquid Glass、圆角和 tint 等公开能力，但风格与 `NSVisualEffectView` 及当前自定义效果不同。首轮不同时维护两个新后端；若原生普通毛玻璃不合适，再单列 Liquid Glass 候选。其 API 可用性和实际效果需在对应 SDK/系统验证，上述总工作量不包含再实现一套候选。

## 6. 官方依据与推理边界

- [NSVisualEffectView](https://developer.apple.com/documentation/appkit/nsvisualeffectview)：材质与混合模式决定外观，behind-window 使用窗后内容，材质并非都具有相同透明特性。
- [NSVisualEffectView.material](https://developer.apple.com/documentation/appkit/nsvisualeffectview/material-swift.property)：外观与材质的关系。
- [NSGlassEffectView](https://developer.apple.com/documentation/appkit/nsglasseffectview)：系统 Liquid Glass 容器及圆角/tint 属性。
- [采用 Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)：系统外观与降低透明度/动态效果等设置会影响材质。
